## 1. 背景与目标

"租租侠"是一个面向社会大众的闲置物品租赁平台，围绕**物品发布、检索、下单、归还、信用评价**构建完整闭环。详细背景见《软件开发计划书》第 1.1 节。

本文档定义项目的**技术底座**，即骨架、接口规范与数据模型三件套。目的是让前端 2 人、后端 2 人在接口冻结后**可以完全并行开工**，避免联调阶段返工。

## 2. 本次交付范围

### 2.1 包含

1. **可运行的工程骨架** —— 前后端各自能独立启动，并跑通一个端到端连通性接口
2. **接口文档** `docs/api/openapi.yaml` —— 全队唯一对接依据
3. **数据库设计** —— 建表脚本、测试数据脚本、ER 说明
4. **公共底座代码** —— 统一响应体、全局异常处理、JWT 认证、前端 axios 封装
5. **一键启动脚本** `scripts/`

### 2.2 不包含

- 具体业务功能的完整实现（由 4 名成员按分工并行开发）
- 公网部署与上线运营（本项目不部署上线，仅本地/局域网演示）

## 3. 技术选型

### 3.1 选型结果

| 层次 | 选型 | 版本 |
|---|---|---|
| 前端框架 | Vue 3（组合式 API） | 3.x |
| 前端构建 | Vite | 5.x+ |
| 前端语言 | **JavaScript**（非 TypeScript） | ES2020+ |
| UI 组件库 | Element Plus | 最新稳定版 |
| 状态管理 | Pinia | 2.x |
| 路由 | Vue Router | 4.x |
| HTTP 客户端 | axios | 1.x |
| 后端框架 | Spring Boot | 3.x |
| 后端语言 | Java | **21** |
| 构建工具 | Maven | 3.9+ |
| 数据访问 | MyBatis-Plus | 3.5.x |
| 认证 | JWT + 拦截器 | jjwt |
| 接口文档 | 手写 OpenAPI 3.0 + 代码侧 Knife4j 注解对齐 | — |
| 数据库 | MySQL | 8.0 |
| 密码加密 | BCrypt | — |

### 3.2 选型理由

- **MyBatis-Plus**：单表 CRUD 零 SQL，复杂查询仍可手写 XML。相比 JPA，复杂联表查询（物品+分类+出租人+信用）更可控，不会陷入 N+1；相比原生 MyBatis，省去大量样板代码。
- **JWT + 拦截器**：无状态，实现成本远低于 Spring Security 全套配置。对 5 人课设团队，Spring Security 的配置曲线是明确的进度风险。
- **手写 OpenAPI 规范先行**：这是"接口先行"原则的落地方式。前端可在**后端一行代码都没写**时，依据 `openapi.yaml` 构造 mock 数据开工。
- **JavaScript 而非 TypeScript**：计划书写明团队"对网站的开发框架和流程熟悉程度不一"。TS 的类型报错会成为前端两人的额外阻塞；课设交付看重主流程跑通，而非类型严谨。

## 4. 架构总览

```
浏览器 (Vue 3 + Vite + Element Plus + Pinia, :5173)
        │  axios  →  /api/**
        ▼
   Vite dev proxy  (解决跨域，前端代码中不写死后端地址)
        │
        ▼
Spring Boot 3 (:8080)  ── JWT 拦截器 ──▶ Controller ─▶ Service ─▶ Mapper ─▶ MySQL 8.0
                                                                  (MyBatis-Plus)
```

### 4.1 三条全局约定（全队强制遵守）

1. **所有接口以 `/api` 开头**。前端 axios `baseURL = '/api'`，由 Vite proxy 转发到 `http://localhost:8080`。
2. **所有响应走统一结构** `{ code, message, data }`，前端只在响应拦截器里判定一次 `code`。
3. **`docs/api/openapi.yaml` 是唯一对接依据**。代码与文档不一致时，以文档为准并修改代码。

## 7. 数据模型

### 7.1 实体关系

```
user ──┬─< item >─── category
       │    ├─< item_image
       │    └─< item_available_period
       ├─< favorite >── item
       ├─< orders (as renter)
       ├─< orders (as owner)
       ├─< wallet_transaction
       └─< review
              orders ──< review
```

**命名注意**：`order` 是 MySQL 保留字，订单表命名为 **`orders`**。

### 7.2 表结构与字段

#### `user` 用户
普通用户与管理员同表，靠 `role` 区分。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT PK | |
| username | VARCHAR(50) UNIQUE | 登录名 |
| password | VARCHAR(100) | BCrypt 加密 |
| nickname | VARCHAR(50) | 昵称 |
| phone | VARCHAR(20) | 手机号 |
| avatar | VARCHAR(255) | 头像 URL |
| role | VARCHAR(20) | `USER` / `ADMIN` |
| status | VARCHAR(20) | `NORMAL` / `BANNED` |
| credit_score | INT | 信用分，初始 100 |
| balance | DECIMAL(10,2) | 可用余额 |
| frozen_balance | DECIMAL(10,2) | 冻结余额 |
| created_at / updated_at | DATETIME | |

#### `category` 分类
| 字段 | 说明 |
|---|---|
| id, name, sort, icon | 分类名、排序、图标 |
| status | 启用 / 停用 |

#### `item` 物品
| 字段 | 说明 |
|---|---|
| id, owner_id, category_id | |
| title, description, location | 标题 / 描述 / 取件地点 |
| daily_price, deposit | 日租金、押金 |
| cover_image | 封面图 URL |
| status | `ON_SHELF` 上架 / `OFF_SHELF` 下架 / `DELISTED` 违规下架 |
| view_count, favorite_count | 热度统计（排行榜用） |
| created_at, updated_at | |

> **说明**：物品"当前是否租用中"**不存入 `item.status`**，而是由 `orders` 中该物品进行中的订单**动态推导**。原因：同一物品在不同日期可分别出租给不同的人，若用全局状态标记，会错误地阻塞非重叠时段的租借申请，与"可租时间段"模型相矛盾。

#### `item_image` 物品图片
id, item_id, url, sort

#### `item_available_period` 可租时间段
id, item_id, start_date, end_date —— 出租人声明的可租区间，可多段。

#### `orders` 订单
| 字段 | 说明 |
|---|---|
| id, order_no | 主键、业务单号（唯一） |
| item_id, owner_id, renter_id | owner_id 冗余，避免查订单时联表 item |
| start_date, end_date, days | 租期与天数 |
| daily_price, rent_amount, deposit_amount, total_amount | **下单时快照**，物品改价不影响历史订单 |
| status | 见 7.3 |
| apply_remark, reject_reason | 申请留言 / 拒绝原因 |
| created_at / confirmed_at / picked_at / returned_at / finished_at / cancelled_at | 各节点时间戳 |

#### `wallet_transaction` 钱包流水
id, user_id, type, amount, balance_after, order_id, remark, created_at

`type` 取值：`RECHARGE` 充值 / `DEPOSIT_FREEZE` 冻结押金 / `DEPOSIT_UNFREEZE` 解冻 / `DEPOSIT_DEDUCT` 扣押金 / `RENT_PAY` 付租金 / `RENT_INCOME` 租金收入 / `DEPOSIT_REFUND` 押金退还

#### `review` 双向评价
id, order_id, reviewer_id, reviewee_id, role(`LENDER`/`RENTER`), score(1–5), content, created_at

唯一索引 `(order_id, reviewer_id)` —— 一单一人只能评一次。

#### `favorite` 收藏
id, user_id, item_id, created_at

唯一索引 `(user_id, item_id)`。

### 7.3 订单状态机

```
                    ┌──(出租人拒绝)──▶ REJECTED ✗
                    │
PENDING ────────────┼──(租用人取消)──▶ CANCELLED ✗
待确认               │
                    └──(出租人同意)──▶ RESERVED ──(租用人确认取件)──▶ RENTING
                                    待取件         │              租用中
                                        │         │                 │
                              (租用人取消)│         │(逾期标记)        │(租用人发起归还)
                                        ▼         ▼                 ▼
                                   CANCELLED   RENTING(逾期)     RETURNING
                                                                待归还确认
                                                                     │
                                                        (出租人确认归还)
                                                                     ▼
                                                                 FINISHED ✓
```

**7 个状态**：`PENDING` / `REJECTED` / `CANCELLED` / `RESERVED` / `RENTING` / `RETURNING` / `FINISHED`

**逾期**：不设独立状态。以 `end_date < 今天 且 status = RENTING` 动态判定并标红。

### 7.4 资金动作时序

| 节点 | 资金动作 |
|---|---|
| 提交申请 `PENDING` | **不动钱**，仅校验余额是否足够 |
| 出租人同意 → `RESERVED` | 扣租金（托管）+ 冻结押金 |
| 拒绝 / 取消 | 解冻押金 + 退还租金 |
| 确认归还 → `FINISHED` | 解冻押金退还租用人；租金入账出租人 |
| 逾期 / 损坏（管理端介入） | 从冻结押金中扣款给出租人 |

### 7.5 并发安全

同一物品同一时段不能被两单占用：

1. 下单时查询 `orders` 中该 `item_id` 与目标时段重叠且状态属于进行中的订单
2. **Service 层加锁**（同一 `item_id` 串行化）
3. **"同意"这一步二次校验**，防止两人同时被同意

## 8. 接口规范

### 8.1 统一响应体

```json
{ "code": 200, "message": "success", "data": { } }
```

### 8.2 分页约定

- 入参：`page`（从 1 开始）、`size`
- 返回：`{ "total": 100, "list": [ ] }`

### 8.3 认证约定

除以下接口外，其余均需请求头 `Authorization: Bearer <token>`：

- `POST /api/auth/login`
- `POST /api/auth/register`
- `GET /api/categories`

物品大厅的**只读**接口同样公开（未登录可浏览）：

- `GET /api/items`、`GET /api/items/{id}`、`GET /api/items/hot`、`GET /api/items/recommend`
- `GET /api/items/{id}/available-periods`

**注意**：`GET /api/items/mine`、`POST /api/items`、`PUT/DELETE /api/items/**` 等写操作与"我的"类接口**必须登录**，不属公开范围。

### 8.4 错误码

| code | 含义 | 触发场景 |
|---|---|---|
| 200 | 成功 | |
| 400 | 参数校验失败 | `@Valid` 不通过 |
| 401 | 未登录 / token 失效 | 拦截器 |
| 403 | 无权限 | 非管理员访问 `/api/admin/**`；操作他人订单 |
| 404 | 资源不存在 | |
| 409 | 通用业务冲突 | |
| 500 | 系统异常 | 兜底 |
| 1001 | 用户名已存在 | 注册 |
| 1002 | 用户名或密码错误 | 登录 |
| 1003 | 余额不足 | 下单 |
| 1004 | 该时段已被租用 | 下单 / 同意 |
| 1005 | 当前订单状态不允许此操作 | 状态机拦截 |
| 1006 | 请勿租借自己的物品 | 下单 |
| 1007 | 订单未完成，无法评价 | 评价 |
| 1008 | 物品已下架 | 下单 |

## 9. 错误处理策略

### 9.1 后端

- `BizException(code, message)` 承载业务异常
- `@RestControllerAdvice` 全局兜底，统一转换为响应体
- `@Valid` 做入参校验
- **状态机非法流转一律抛 1005**，绝不在 Controller 里写 if 判断

### 9.2 前端

- `request.js` 响应拦截器统一处理：
  - `401` → 清除 token，跳转登录页
  - 其他 `code !== 200` → `ElMessage.error(message)`
  - `code === 200` → `return data`
- **后端返回的 `message` 就是给用户看的中文提示**，前端不再自行拼错误文案，避免两端文案不一致

## 11. 强制约定

1. **接口先行**：`openapi.yaml` 未定义的接口不得实现；接口变更须当天同步文档并通知全员
2. **前后端并行**：接口冻结后，前端用 mock 数据先行开发，后端独立实现，互不阻塞
3. **不写裸错误码**：业务码一律走 `ResultCode` 枚举
4. **不在 Controller 写业务逻辑**：状态判断、金额计算一律在 Service 层
5. **金额一律 `BigDecimal`**，禁止用 `double` / `float`
6. **不提交生成物**：`node_modules/`、`target/`、`.idea/`、`uploads/`、`application-local.yml`
